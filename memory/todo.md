## Follow-ups from the code reviews of 2026-11-16
- [x] Scrolling: a drag is told from a tap. The content waits until the pointer has gone `SLOP` (8 surface pixels) along a Layout; a press that has moved a Layout at any level is a scroll, and until it is let go every Listener in the instance has the pointer as gone, while the Layouts held go on following (`instance.rs: pointer`, `drags`, `hear`, `scroll`; `features.rs: a_drag_that_scrolls_is_not_a_tap`; tried with a mouse in Chromium)
- [x] Scrolling: the host says how far a press may go before it scrolls: `Instance::set_drag_threshold`, C ABI `zuri_instance_set_drag_threshold` (8 surface pixels until set), web `Instance.setDragThreshold`, Unity `ZuriInstance.SetDragThreshold`, Unreal `UZuriInstance::SetDragThreshold`. The web player sets it at every press (`dragThreshold`, exported, which the editor's preview uses too): 4 CSS pixels for a mouse, 10 for a finger or a pen, times the canvas's pixels per CSS pixel (`features.rs: a_drag_that_scrolls_is_not_a_tap`, `smoke.c`, web `runtime.test.mjs` and `browser.html`, the Unity harness, Unreal `Zuri.Scroll`). Not tried with a real finger
- [x] One pointer and one button, in the runtime: `Instance::pointer_of(pointer, button, kind, x, y)`; the C ABI's one pointer call, `zuri_instance_pointer(inst, kind, x, y, pointer, button)`, returns whether the event was the scene's (web `Instance.pointer(kind, x, y, pointer, button)`, Unity `ZuriInstance.Pointer` / `ZuriPlayer.Pointer`, Unreal `PointerDown(Position, Pointer, Button)` and the others). A press begins when a primary button goes down and ends when it goes up or its pointer leaves; meanwhile no other pointer is the scene's, nor one that came down beside the press until it is let go, nor another button. The hosts pass every event on and keep no rule of their own (`features.rs: the_scene_has_one_pointer_and_one_button`, `smoke.c`, web `runtime.test.mjs` and `browser.html`, the Unity harness and PlayMode, Unreal `Zuri.Scroll` and `Zuri.Widget`)
- [x] The engines' own components set the drag threshold when a press is taken: Unity's `ZuriPointerSurface` from the EventSystem's `pixelDragThreshold` in texture pixels, Unreal's `SZuriWidget` from Slate's drag trigger distance (screen pixels, which the render target's are). Each ends a press that came through it and can no longer be let go through it, as that pointer leaving: Unity when a release cannot be placed or the surface is disabled, Unreal when Slate takes the capture away in the middle of a press. A host that feeds the pointer itself sets its own threshold, per instance
- [ ] Unity: where a view stretches the texture unevenly, the threshold is the EventSystem's along the axis with more texture pixels to the screen pixel, so a Layout that scrolls along the other needs more travel than the EventSystem asks (a 320 x 160 view of an 80 x 120 texture: three times as much sideways). One threshold per axis in the runtime would fix it; an unevenly stretched view distorts the picture anyway
- [ ] Pointer: what is on top does not shield what is under it. The Listeners, the press that scrolls and the wheel each go to everything under the pointer, and a nested artboard's Layouts before its parent's own: a drawer that scrolls over a feed moves the feed first, and a list under a panel still scrolls. Needs the topmost thing under the pointer (in drawing order, through nested artboards) and a way to say that it stops the pointer. Found by code review 2026-11-17
- [ ] Wheel: hover is as of the last pointer event, so a row that the wheel (or an animation) moves from under a still pointer stays hovered until the pointer moves; a host could tell the scene the pointer's place again after the advance. The web player has no option to leave the wheel to the page, and a gesture that reaches a list's end goes on to the page at once (no latching to what it began on). Found by code review 2026-11-17
- [ ] Scrolling: a Layout whose `scrolled` an animation keys counts as moved while a press goes along it although the key puts it back, so the press is lost to what is in it (`ponytail:` note on `Instance::scroll`). Not holding a Layout that the playing animation keys needs the tracks looked up at the press The wheel over such a Layout is always taken (it moves, and the key puts it back), so the page does not scroll there
- [ ] Pointer, what is left: a pointer remembered beside a press is forgotten when it leaves as well as when it is let go, so a finger that came down beside a press, slid off the surface and lifted is heard lifting (kept so: the other way a mouse whose release beside a press was missed would stay unheard). - [ ] Pointer: a release that the host never reports leaves the press open: the Layouts held follow the hover, and after a scroll the Listeners hear nothing until the next press, release or exit. - [~] Lists, cost: an artboard that has nowhere to show is not outlined or drawn (a copy that clips, as one does unless told not to, and is out of its box's reach), and a clip narrows what is drawn to its own box while it lasts (2026-11-17): 2000 rows that clip draw in 0.35 ms where they took 7.0 (`features.rs: a_copy_that_is_out_of_sight_is_not_drawn`, `docs/dev/rendering.md`). `examples/rows.json` gets nothing of it: its Row says `"clip": false` for the outline of the chosen row, and a copy that does not clip is drawn wherever it is (its content's box is not known without outlining it). ## Known issues and debt
- `grep -rn "ponytail:" crates packages` lists every deliberate shortcut with its upgrade path (38 on 2026-11-17).
- **Researched on 2026-11-17**; measured on an Apple M4, one core; sources in that day's handover entry. In order of what the measurements say is worth doing:
  1. **Software 3D at full-screen sizes**: done in part on 2026-11-17 (the handover of that day; times in `docs/dev/rendering.md`). Left, if 3D at such sizes matters: edge functions in whole numbers with a top-left rule, which can be stepped along a row without the gaps that stepping floats opened (tried that day: 12.7 ms, and cracks along shared edges), then one sample per pixel with the edges alone smoothed, then SIMD (`core::arch`; `std::simd` is not stable); a GPU for the layer where the host has one is what Rive and Spline do (Rive draws 3D on its GPU canvas only).
  2. **Imported SVG shapes had baked transforms**: done on 2026-11-17 (`zuri-import/src/svg.rs`, `import.rs: svg_groups_keep_their_transforms_to_animate`, `docs/user/importing.md`, the handover of that day). Not tried: a file exported by a drawing program.
  3. **The pointer that did nothing on a first load** (2026-11-16, once, on a scratch page tried in Chromium: no click, no scroll; ten later loads were right, and the page did not record which events arrived). Likeliest by the research: events sent before the player had attached its listeners (the first load compiles the wasm cold; later ones have it cached). It cannot be shown after the fact. `ZuriPlayer.create` resolving is the "ready" there is; a test or a page must wait for it. Looked at and left: a canvas with no size yet makes the pointer's place infinite, which hits nothing, as no event would; a guard there would change nothing that can be seen.
  4. **Clips**: done as far as it pays (2026-11-17, with the lists above). The register's "full-surface mask every frame" was half right: the coverage was worked out inside the scissor only, but the whole mask was zeroed for every clip. A clip now narrows the scissor to its own box while it lasts and its mask is no longer zeroed (it is read only where it is written). Left, if clips show in a profile: an upright clip on whole pixels as a scissor with no mask (what Skia, Cairo and Qt do; `draw.rs` already does it for an artboard).
  5. **Shader paints on the web**: one readback per paint per frame, a frame late. Instances of a component share one texture, of the first one's size and parameters: a larger copy shows it blurred. Asking for the largest size instead was tried on 2026-11-17 and taken back on review: small copies would then alias (the sampler blends four pixels and no more), and the largest width with the largest height can be a shape that no copy has. The fix is a texture per instance (a request keyed by the instance's path, which changes what `zuri_instance_shader_request` hands out). Nobody found pairs a CPU rasterizer with shaders read back (Rive and Flutter need their GPU renderers; Skia's CPU path is an interpreter). Left, in the host alone: no redraw while uniforms and size are unchanged, MDN's asynchronous read (`PIXEL_PACK_BUFFER` and a fence) if the stall is measured. A GPU compositor in the web package gives the same frame and no readback, and costs a WebGL context per canvas and care about what is drawn above a shader paint.
  6. **Unity handles**: keep `IntPtr` + `Dispose` + finalizer + `GC.KeepAlive` (rive-unity does the same for most of its types); a SafeHandle behind `IntPtr` signatures with AddRef / Release at each call is more code per call and as easy to forget. No call was missing a `KeepAlive` on 2026-11-17, and the harness now reads the two wrappers' source and fails where a member reads the native pointer and does not say `GC.KeepAlive(this)` after its last reading (`Program.cs: KeptAlive`). Not done: a run under a collector that is made to collect during calls.
  7. A lint for the `ponytail:` markers (ids, severities, a register kept in step): not doing; the markers are found by `grep` and say their own upgrade path.
